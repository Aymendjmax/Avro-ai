# Operating Modes: Ask vs Work Architecture Contract

## Overview

Agora provides two distinct conversation operating modes:
- **Ask Mode**: Conversational, advisory mode. Shell command execution and file manipulation tools are strictly disabled to prevent unintended side effects and conserve token budget.
- **Work Mode**: Autonomous agent environment. Equips the model with tools for local execution in an on-device PRoot Alpine Linux 3.21 sandbox or configured Conch servers, persistent workspace mounting, and local visual inspection (`view_image`).

## Tool Isolation Contract

1. **Ask Mode Isolation**:
   - `ShellToolDefinitions.build(ctx)` returns an empty list when `shellEnabled = false` or when operating in Ask mode.
   - System prompts explicitly instruct the model that shell execution is disabled.
2. **Work Mode Activation**:
   - Shell and local filesystem tools (`list_shells`, `execute_shell_command`, `file_read`, `file_write`, `file_edit`, `file_glob`, `file_grep`, `view_image`) are only presented if shell tools are enabled and the local sandbox or remote servers are ready.
   - If the sandbox is not installed or shell is disabled, the system prompt explicitly informs the model that shell tools are unavailable, and a warning is displayed in the UI.

## Environment Contract

- **OS / Rootfs**: Alpine Linux 3.21 on-device via PRoot.
- **C Library & Shell**: musl libc and busybox (`ash`).
- **Package Management**: Alpine `apk` (`apk add --no-cache <package>`).
- **Workspace Directories**:
  - `/home/uploads/<chatId>`: Uploaded conversation attachments.
  - `/home/outputs/<chatId>`: Artifacts generated by commands.
  - `/home/projects`: Cross-conversation user repositories and projects.
  - `/home/notes`: Persistent notes and scratchpad.

## Mode Transition & `request_work` Tool Contract

When a user in **Ask Mode** requests tasks that inherently require terminal execution, code file creation/editing on disk, package installation via `apk`, or script execution, the model is equipped with the `request_work(reason)` tool:
- **Tool Availability**: Available exclusively in Ask mode (`ConversationMode.ASK`). In Work mode, full shell tools are already exposed.
- **Interactive Handshake**: Invoking `request_work` triggers a suspend in generation and presents an interactive `DeckPage.Work` transition card in the chat interface via `UserInteractionBar`.
- **Card Elements**: Displays the model's reason, the current Alpine Linux PRoot sandbox installation status (or download/install progress indicator if first-time), an action button to "Enable Work & Continue" (`work_mode_enable_and_continue`), and a dismiss button to "Stay in Ask" (`work_mode_stay_in_ask`).
- **Approval Flow**: If accepted, conversation mode transitions to `ConversationMode.WORK`, any missing sandbox packages are initiated, and `request_work` completes with status `"accepted"`. In subsequent turns, full shell and file tools are active.
- **Decline Flow**: If declined, `request_work` completes with status `"declined"`, and the controller remembers the decline for the current turn to prevent repetitive tool call loops. The model continues conversationally.

## Visual Inspection (`view_image`)

In Work mode, models can visually inspect images located in the local sandbox (`/home/uploads`, `/home/outputs`, etc.):
- **Vision Models**: Direct visual context with downscaling to ~1500px JPEG.
- **Non-Vision Models**: Fallback secondary image reader with layered prompts (`document`, `ui`, `code`, `diagram`, `general`) and SHA-256 caching. Output is explicitly labeled as untrusted machine description.

## Prompt Composition & Variable Integration

Work Mode directives and environment paths are dynamically composed into the system prompt:
1. **Predefined Variables**:
   - `{work_environment}`: Resolves to sandbox filesystem paths, upload directories (`/home/uploads/<chatId>`), and package manager instructions.
   - `{work_rules}`: Resolves to autonomous execution directives (inspect first, non-interactive flags, mandatory verification).
2. **Automatic Injection & Deduplication**:
   - If the user customizes the System Prompt template and explicitly positions `{work_environment}` or `{work_rules}`, those variables are expanded at their designated positions.
   - Any omitted piece is automatically appended inside an `<operating_mode>` section at the end of the system prompt to guarantee the model always knows it operates in an autonomous Linux environment.
   - If both variables are explicitly included, no redundant text is appended.
3. **Compact Mode for Local Models & Low-Context**:
   - When running against local models (e.g. `Constants.PROVIDER_LOCAL` / llama.cpp) or when Low Context Mode is active, a compressed, token-efficient variant of the environment and directives is used (<300 tokens) to preserve the device's constrained context window.

## Dedicated Work Mode Settings (`SettingsWorkPage`)

To provide unified governance over the autonomous agent environment, `SettingsWorkPage` provides:
1. **Operating Mode Defaults**: Configures default mode for newly initiated conversations (`ask` or `work`).
2. **`request_work` Activation**: Allows toggling the model's ability to request Work mode escalation.
3. **Sandbox Runtime Controls**: Displays Alpine Linux 3.21 PRoot status with one-tap navigation to the detailed sandbox manager.
4. **Tool Toggles**: Controls `view_image` inspection and MCP file reference bridging.
5. **Storage Analytics & Cleanup**: Live asynchronous calculation of storage used across `/home/uploads`, `/home/outputs`, and `/home/projects` with guarded dialogs for clearing outputs, uploads, or executing a complete workspace reset.
